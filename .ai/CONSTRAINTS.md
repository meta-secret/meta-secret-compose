## 🚨 Core Constraints (Must Know)

### Vault Model
- **Vault** = trusted group of user's devices
- User starts with 1 device and may add devices until the Vault has 3 devices
- A fourth or later device is rejected by Core; UI displays the returned error
- With 1 device the Secret is stored whole; with 2 devices it is fully replicated; with 3 devices it uses **Shamir Secret Sharing**
- Sharing scheme: **k = 2 for 3 devices**; 1 device is trivial and 2 devices use full replication with k=1
  - 1 device → whole secret locally
  - 2 devices → k=1 full replication (either device alone can recover)
  - 3 devices → 2-of-3 (any 2 shares needed)

### Device Master Key (DMK)
- Generated by Core, unique per device
- Must be saved on device in hardware-backed secure storage
  - **iOS:** Keychain (`kSecAttrSynchronizable: false`) — survives reinstall, no iCloud sync
  - **Android:** AES-256-GCM encrypted file in `noBackupFilesDir`, key in Android Keystore — does NOT survive reinstall (accepted behavior)
- Used to create AppManager and restore database
- NOT transmitted to server
- NOT a password, NOT a share, NOT Vault key
- NOT synced to cloud on either platform

### Server (What it does NOT do)
- ❌ Never stores plaintext Secrets or Key Shares
- ✅ May temporarily queue Claim metadata and Encrypted Key Shares while delivery/synchronization is pending; the Encrypted Key Share is removed after delivery and the server must not be able to decrypt it
- ❌ Never stores Device Master Key
- ❌ Never stores device database
- ✅ Only: signaling, message delivery, device communication

### Shamir Secret Sharing
- Each user secret splits **separately** (not one Vault key)
- Not used with 1 device (secret stored whole)
- 1 device: k=1; 2 devices: k=1 full replication; 3 devices: k=2
- Old shares invalid after resharing
- In a 3-device Vault each device stores only its own Key Share. Remote encrypted
  shares are temporary outbound workflows and are removed from the sender's local
  database after successful upload.

## ⚡ Quick Reference

**Never allow:**
- ❌ Server storing plaintext Secrets, Key Shares, or Master Keys
- ❌ Vault Data Key usage
- ❌ Recovery Key usage
- ❌ Bypassing constraint validation (Stage 3.5)
- ❌ Deviations from the k=1 / k=1 / k=2 device-count policy
- ❌ Device removing itself
- ❌ Removing last device

**Recovery decision ordering:**
- ✅ If the first server-processed receiver decision is `DECLINE`, remaining pending receivers become terminally declined and the sender must not reveal the secret.
- ✅ If the first decision is `APPROVE`, the approving receiver reaches `SENT`/`DELIVERED` and a later `DECLINE` cannot revoke recovery.
- ✅ Web, iOS, and Android render the `clientStatus`/claim state supplied by Core; UI code must not implement its own quorum or race resolution.
- ❌ Cloud backup/sync of any app data (DMK, DB, keys)
- ❌ Storing DMK in external storage or plaintext

**Always require:**
- ✅ Approval for join/remove
- ✅ Resharing before removal
- ✅ DMK saved to hardware-backed secure storage (Keychain / Android Keystore)
- ✅ DB file deleted on clearAll (including files from old master keys)
- ✅ Biometry or PIN for operations
- ✅ Constraint validation before coding
